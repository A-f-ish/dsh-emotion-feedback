# Publishing checklist

Everything here is meant to be run by the package owner (`A-f-ish`); the plugin itself needs no build step.
The package identity is already filled in: `repository`/`homepage`/`bugs` point at
`https://github.com/A-f-ish/dsh-emotion-feedback` and `author` is `A-f-ish`.

## 0. Prerequisites

- A GitHub account named **`A-f-ish`** and an (initially empty) repository named **`dsh-emotion-feedback`**.
- The npm package name **`dsh-emotion-feedback`** must still be unclaimed. Re-check right before publishing:

  ```powershell
  npm view dsh-emotion-feedback version    # 404 == still free; if taken, rename in package.json + cordis.patch.yml
  ```

- Before the first push, confirm the metadata is still consistent:

  ```powershell
  node scripts/validate.mjs      # must print 结论：通过 with no warnings
  ```

## 1. Create the repository

```powershell
git init
git add .
git commit -m "dsh-emotion-feedback 0.1.0"
git branch -M main
git remote add origin https://github.com/A-f-ish/dsh-emotion-feedback.git
git push -u origin main
```

Then add the topic **`dsh-plugin`** to the repository (Settings → Topics). That topic is where the community
registry points for discovery: <https://github.com/topics/dsh-plugin>.

## 2. Publish to npm

```powershell
npm login                                  # if not logged in yet
npm pack --dry-run                         # inspect the exact file list that will be published
npm publish                                # publishConfig.access = "public" is already set
npm view dsh-emotion-feedback version      # verify
```

`npm pack --dry-run` only needs a writable cache. In a sandboxed workspace where the global npm cache is not
writable, point it inside the repo:

```powershell
$env:npm_config_cache = "$PWD\.npm-pack-cache"
npm pack --dry-run
Remove-Item .npm-pack-cache -Recurse -Force
```

After publishing, users install it directly:

```powershell
dsh plugin --profile <profile> add dsh-emotion-feedback
```

## 3. Submit to the community registry (awesome-dsh-plugin)

The registry at <https://awesome-dsh-plugin.com/plugins.json> (4700+ plugins) is what the `dshmarket`
marketplace plugin reads. Submission = **one new YAML file, one PR**:

1. Fork <https://github.com/awesome-dsh-plugin/awesome-dsh-plugin>.
2. Add `data/plugins/A-f-ish__dsh-emotion-feedback.yml` — the file name is `<owner>__<repo>` with a double
   underscore. Use `docs/registry-entry.yml` here as the content template.
3. Open a PR. The repository's `README.md` is generated by a script — do not edit it.

Hard requirements (most rejections are the first one):

- the repository's `package.json` must declare **`dsh.bundle`** — declaring only `dsh.client` is the single
  most common rejection reason (this package declares both);
- a `cordis.patch.yml` at the repository root containing an `- insert:` list with `- id: <id>` and
  `- name: <package name>` (this package ships exactly that);
- the entry's `url` must match the repository exactly;
- `description.en` is the only required description field (`zh` is optional and may be filled by maintainers);
- do **not** hand-write an `npm:` field — the registry collects it automatically, and a hand-written one is
  rejected by their validation.

## 4. Optional extras

- Theme/skin-style plugins belong in the `theme` category so they land in dsh-market's Themes tab; this plugin
  is not one, so it uses `category: ui`.
- Publishing to npm makes the package installable by name; the registry entry makes it discoverable in the
  marketplace UI. Both are independent.
